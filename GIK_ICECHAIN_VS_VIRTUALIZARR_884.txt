GIK-IceChain — Response to VirtualiZarr #884 / icpac-igad Discussion #1
==========================================================================
Date: 2026-06-05
Authors: hashirama21, dylan-baf, nehdf-gif (SYNTHI-AI / E4DRR)


CONTEXT
-------
VirtualiZarr #884 and the ICPAC discussion raise three core problems when
converting large GRIB2/NetCDF archives (CMORPH, ECMWF IFS ENS) to IceChunk:

  1. OOM crash when writing virtual references directly to IceChunk at scale
  2. append_dim="time" memory blow-up on living datasets
  3. No manifest splitting -> single growing manifest -> degrading append speed

This document explains which problems gik-icechain solves, how, and which
remain open.


===========================================================================
PROBLEM 1: OOM WHEN WRITING VIRTUAL REFS TO ICECHUNK AT SCALE
===========================================================================

BACKGROUND (from #884)
-----------------------
nishadhka tried three strategies to write 236,688 CMORPH NetCDF virtual
references directly into an IceChunk store:

  - Batch mode:  workers virtualize files, xr.concat, write per-branch
  - Collect mode: coordinator collects refs, single to_icechunk() commit
  - Direct mode:  each worker commits independently

All three failed with OOM (exit 137) at ~28,000/236,688 files because the
coordinator accumulated ~85 KB of Kerchunk JSON per file in memory:
  28,000 files x 85 KB = ~2.4 GB at failure point
  236,688 files x 85 KB = ~20 GB at full scale

The workaround: PyArrow streaming ParquetWriter flushes each batch to disk
immediately, keeping coordinator RAM constant at ~10 MB.

HOW GIK-ICECHAIN SOLVES IT
---------------------------
gik-icechain avoids the OOM entirely through a different architecture:

  [1] PRE-BUILT PARQUET CATALOG (HuggingFace: E4DRR/gik-ecmwf-par)
      The Kerchunk references for ECMWF IFS ENS are already materialized
      as a flat-parquet catalog on HuggingFace. Each row encodes one
      (date, run_hour, member, step, variable) chunk ref as a byte array.
      This catalog was built incrementally as forecasts arrived — it is
      never rebuilt from scratch.

  [2] PER-DAY STREAMING VIRTUALIZATION (src/gik_icechain/conversion/)
      C1 processes one forecast day at a time:
        - Load 51 parquet files (one per ensemble member) via ThreadPoolExecutor
        - Parse with GIKFlatParquetParser -> ManifestStore (VirtualiZarr)
        - xr.concat along member dimension -> single virtual Dataset
        - commit_day() -> one IceChunk commit
      Memory per day: ~51 parquet files x ~a few KB refs = negligible.
      The coordinator never holds more than 1 day of refs in memory.

  [3] FREQUENT PARTIAL COMMITS
      One commit per forecast day, tagged with ISO-8601 timestamp:
        "2025-02-22T00Z" -> IceChunk snapshot SS9FE3YY38SV
      This is exactly what TomNicholas recommended in #884:
        "batching the files, and making partial, frequent commits"

STATUS: SOLVED
The OOM problem does not occur in gik-icechain because:
  - We never accumulate 236K file refs in memory at once
  - One day = 51 members x 85 steps x 5 variables = ~21,675 chunk refs
  - Committed immediately, freed from memory before next day starts


===========================================================================
PROBLEM 2: append_dim="time" MEMORY BLOW-UP ON LIVING DATASETS
===========================================================================

BACKGROUND (from #884)
-----------------------
VirtualiZarr's append_dim="time" approach failed at ~87,000 timesteps
because each new append reads back O(n) metadata (all existing time coords)
before writing, causing memory to scale with dataset size.

HOW GIK-ICECHAIN SOLVES IT
---------------------------
gik-icechain does not use append_dim="time" from VirtualiZarr.
Instead it uses IceChunk's native transaction model:

  session = repo.writable_session(branch="main")
  zarr_group = zarr.open_group(session.store, mode="a")
  # Write new day's data into a NEW date-keyed Zarr group
  day_group = zarr_group.require_group(date_str)
  session.commit(f"GIK ingest: {date_str}T{run_hour:02d}Z")

Each forecast day occupies its own Zarr group (keyed by ISO date string,
e.g. "2025-02-22"). There is no single time-dimension array that grows.
This sidesteps the O(n) metadata read entirely: appending day N+1 only
touches group "2025-02-23", not the existing 2025-02-22 group.

RESULT:
  - Memory for commit_day() is constant regardless of total days in store
  - 1200 days of IFS ENS = same RAM as 1 day during append
  - IceChunk's transaction log records snapshot history for rollback/replay

STATUS: SOLVED
The append_dim blow-up does not affect gik-icechain because the temporal
dimension is encoded as group keys (date strings), not as a zarr array
dimension. Each day is an independent write with no O(n) metadata scan.


===========================================================================
PROBLEM 3: MANIFEST SPLITTING
===========================================================================

BACKGROUND (from #884)
-----------------------
TomNicholas recommended manifest splitting along the time dimension to
prevent the IceChunk manifest from becoming a single growing file that
slows append and metadata scan as the archive grows.

IceChunk 2.x exposes ManifestSplittingConfig for exactly this purpose.

STATUS: NOT YET IMPLEMENTED IN GIK-ICECHAIN

Current state:
  - icechunk_writer._build_repo_config() does not set ManifestSplittingConfig
  - All VirtualChunkRefs for all committed days accumulate in one manifest
  - For small runs (< 100 days) this is not yet a bottleneck
  - At 1200 days x 21,675 refs/day = ~26 million refs, manifest size and
    append latency will degrade without splitting

Required fix (icechunk_writer.py):

  from icechunk import (
      ManifestConfig, ManifestSplittingConfig, ManifestSplitCondition
  )

  def _build_repo_config(self) -> RepositoryConfig:
      return RepositoryConfig(
          manifest=ManifestConfig(
              splitting=ManifestSplittingConfig(
                  condition=ManifestSplitCondition.split_after_n_chunks(1000)
              )
          ),
          ...
      )

  Splitting by 1000 chunks per manifest file would give ~27 files for a
  1200-day store instead of one growing monolith.

IMPACT: Low for current scale (< 50 committed days), high at 1200+ days.


===========================================================================
ADDITIONAL OPEN ISSUES DISCOVERED DURING DEVELOPMENT
===========================================================================

ISSUE A: ECMWF S3 PUBLIC DATA RETENTION (~15 MONTHS)
------------------------------------------------------
The GIK HuggingFace catalog covers 2024-03-01 to 2026-02-18 (720 days).
The public ECMWF S3 bucket (s3://ecmwf-forecasts) retains forecast data
for approximately 15 months. Dates older than ~15 months return 403
Forbidden when byte-range reads are attempted in C2 (exceedance).

Consequence:
  - C1 (ingest virtual refs): works for all catalog dates (metadata only)
  - C2 (fetch GRIB2 bytes for exceedance): works only for last ~15 months
  - Historical flood validation on 2024-04-26 (Kenya MAM floods): Forbidden

Solution for full historical archive: ECMWF subscription (MARS archive
access) or local GRIB2 mirror for dates older than 15 months.

ISSUE B: AWS_ENDPOINT_URL COLLISION (FIXED: commit d051604)
------------------------------------------------------------
Running the pipeline sets AWS_ENDPOINT_URL=http://MinIO-IP:9000 for
IceChunk to write to local MinIO. The manifest-aware C2 path uses
fsspec.filesystem("s3") which inherits this env var, redirecting all
ECMWF S3 byte-range reads to MinIO (403 Forbidden).

Fix: explicit endpoint_url in byte_range.py client_kwargs:
  client_kwargs={
      "region_name": s3_region,
      "endpoint_url": f"https://s3.{s3_region}.amazonaws.com",
  }
This overrides AWS_ENDPOINT_URL for ECMWF reads only.
The same fix was previously applied to IceChunk's Rust S3 client
in icechunk_writer._build_repo_config().

ISSUE C: ICECHUNK 2.x API MIGRATION (FIXED: commits f19d56f, d051604)
----------------------------------------------------------------------
IceChunk 2.0.5 changed all_virtual_chunk_locations() from returning a
{chunk_key: location} dict to returning a flat list of unique URIs.
This broke the manifest-aware C2 loader which needed (url, offset, length)
per chunk.

Fix: ported _extract_virtual_chunk_refs() to use
store.array_chunk_iterator(array_path) which yields batches of:
  (coords, types, uris, offsets, lengths, extra)
providing (url, offset, length) per virtual chunk without any S3 fetch.
Validated: 1530 refs extracted correctly for 2024-04-26.

ISSUE D: CLUSTER DISPATCH IN C3 (FIXED: commit d8e2c19)
--------------------------------------------------------
CRMAModel was instantiated with a single climate cluster (EQUATORIAL_EAST)
applied to all 155 admin-1 units. Units in Somalia (horn_arid), Ethiopia
(great_rift), South Sudan (nile_basin) received CPT weights calibrated for
equatorial Kenya/Tanzania — scientifically incorrect for ~80% of units.

Fix: _build_pcode_cluster_map() maps each admin-1 pcode to its correct
EastAfricaCluster via ISO3 country code (from shapeGroup column).
One CRMAModel per cluster is built and dispatched per unit in _process_day().

===========================================================================
RECOMMENDED NEXT STEP FOR THE ICPAC DISCUSSION
===========================================================================

The "small starting step" proposed by nishadhka (1 variable + 1 month +
1 member, batched commits + manifest splitting) is validated by gik-icechain
at larger scale. The key insight to share with the icpac-igad discussion:

  The OOM is not intrinsic to IceChunk virtual stores — it only occurs when
  all references are written in a single transaction. Writing N chunks in
  B-chunk batches with frequent commits and date-keyed group structure keeps
  memory constant at O(B), not O(N).

  For 236K CMORPH files: split by day (one commit per ~480 30-min files),
  not by batch of arbitrary size. IceChunk's snapshot history then gives
  you a time-indexed transaction log for free.

  Open item: add ManifestSplittingConfig to avoid the single-manifest
  bottleneck at full 25-year scale.
