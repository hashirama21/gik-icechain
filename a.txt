
  ## V. Pré-calcul offline des excédances comme artefact versionné dans IceChunk

  C'est la piste qui réconcilie le principe "zéro duplication" avec la réalité opérationnelle.

  La proposition promet time-travel sur les données. Mais la vraie valeur opérationnelle n'est pas de pouvoir rejouer l'accès aux données brutes GRIB2 à une date passée — c'est de pouvoir rejouer
  les décisions de risque. Les météorologistes ICPAC n'ont pas besoin de ré-accéder aux données brutes du 25 octobre 2023. Ils ont besoin de savoir quelle était la probabilité d'excédance calculée
  ce jour-là avec les données disponibles à ce moment.

  Le changement architectural est le suivant : IceChunk ne stocke plus des manifests vers les GRIB2 bruts. IceChunk stocke les probabilités d'excédance calculées (output de C2) et les scores de
  risque admin-1 (output de C3), versionnés avec les snapshots quotidiens. Les données GRIB2 brutes restent accessibles via les Parquet GIK pour quiconque veut reprocesser.

  Cela réduit le volume du store IceChunk de 18.5 GB de manifests à environ 300 MB de probabilités d'excédance pour 1 200 jours (date × lat × lon × window × return_period en float32 compressé). Le
  time-travel s'applique à ce qui compte vraiment — les décisions — pas aux données sources qui sont immuables sur S3 ECMWF de toute façon.

  C'est architecturalement la Solution C du document précédent, mais formulée différemment : pas comme un abandon, mais comme un choix délibéré de versionner les artefacts de décision plutôt que les
   données sources.

  3. La contrainte fondamentale non résolue : les chunks GRIB2

  C'est le problème central du projet. Il conditionne la viabilité opérationnelle de C2.

  Le fait : Chaque message GRIB2 ECMWF encode la grille globale 721×1440 en un seul bloc Data Section (~1 MB compressé). Les byte-ranges dans les Parquet GIK pointent vers des messages GRIB2 entiers. Un
  chunk virtuel IceChunk = un message GRIB2 = la grille globale.

  Conséquence : _subset_to_bbox() dans cli.py:101-136 est un leurre. Le subsetting spatial s'applique après le téléchargement du chunk complet. Pour 50 membres × 85 steps = 4 250 messages × ~1 MB = ~4 GB
   par jour. Sur 1 200 jours rétrospectifs, c'est ~4.8 TB de transfert réseau.

  Le _subset_to_bbox() ne réduit pas le transfert, il réduit seulement la mémoire après décodage. Le commentaire dans cli.py:233-235 ("reduces transferred data by ~97%") est incorrect — il réduit la
  mémoire de travail, pas le volume réseau.

  Impact : Le pipeline C2 batch est infaisable en streaming pur depuis un poste de travail. Les timeouts et connection resets rencontrés pendant le développement en sont la preuve directe.

  4. Pistes de résolution de la contrainte GRIB2

  a) Pré-agrégation spatiale admin-1 (Piste III de votre analyse)

  C'est la piste la plus immédiatement implémentable. Au lieu de :

  GRIB2 global → décode 721×1440 → subset EA → excédance pixel → agrège admin-1

  On fait :

  GRIB2 global → décode 721×1440 → masque admin-1 → précip moyenne par polygone → excédance admin-1

  Le code existe déjà dans aggregator.py (aggregate_to_admin1, coverage_fraction). Il faudrait le déplacer avant le calcul d'excédance au lieu d'après. On passe de 141×141 matrices par membre par step à
  300 scalaires. Le transfert reste identique (~4 GB/jour) mais la mémoire chute de ~100×.

  L'implémentation nécessiterait ~50 lignes de modification dans _run_exceedance() et exceedance.py.

  b) Parallélisme inter-jours (Piste IV)

  _run_exceedance() dans cli.py:165-292 traite les jours séquentiellement via un for date_str in committed_dates. Passer à un ProcessPoolExecutor avec 32 workers sur une VM cloud dans eu-central-1 divise
   le temps total par ~32×. C'est ~20 lignes de modification.

  Attention : le IceChainStore avec _clear_aws_credential_env() est un singleton qui modifie os.environ globalement (icechunk_writer.py:109-111). En multi-process, chaque worker hérite d'un environnement
   propre via fork, donc ça fonctionne. Mais en multi-thread, c'est une race condition.

  c) Versionner les artefacts de décision plutôt que les données sources (Piste V)

  C'est le changement architectural le plus profond. IceChunk stockerait les probabilités d'excédance (output C2) et les scores de risque admin-1 (output C3) au lieu des manifests vers les GRIB2 bruts.

  Volume : ~300 MB pour 1 200 jours (date × lat × lon × window × return_period en float32 compressé) au lieu de 18.5 GB de manifests. Le time-travel s'applique à ce qui a de la valeur — les décisions —
  pas aux données sources immuables sur S3 ECMWF.

  d) Analyse CCSDS/JPEG2000 (Piste I)

  Les messages GRIB2 ECMWF avec CCSDS ou JPEG2000 encodent par blocs de lignes. Si c'est le cas pour tp et ro, un byte-range ciblé sur les 141 lignes East Africa est théoriquement possible. C'est une
  investigation — pas un engagement.

  e) VirtualChunkSpec rechunking (Piste II)

  IceChunk 2.x pourrait exposer des chunks logiques (141×141 East Africa) tout en stockant des byte-ranges vers des messages globaux (721×1440). Le codec décoderait le message complet puis retournerait
  la sous-région. Pas de réduction réseau, mais l'interface C2 voit un dataset EA natif. Ergonomie + mémoire.

  5. Bugs et problèmes techniques concrets

  a) _clear_aws_credential_env() est destructif (icechunk_writer.py:98-111)

  for key in ("AWS_ACCESS_KEY_ID", "AWS_SECRET_ACCESS_KEY",
               "AWS_SESSION_TOKEN", "AWS_ENDPOINT_URL"):
      os.environ.pop(key, None)

  Cette méthode modifie irréversiblement l'environnement du processus. Si un autre composant du même processus a besoin de ces variables (boto3 pour GPM IMERG, par exemple), il sera cassé
  silencieusement. La solution correcte serait un context manager qui restaure les variables, ou mieux, l'isolation par sous-processus.

  b) _threshold_bbox() accède à des attributs internes (cli.py:149-151)

  for mode_key in thresholds._thresholds:
      for wh in thresholds._thresholds[mode_key]:

  Accède directement à _thresholds (underscore = privé). Si AdaptiveGEVThresholds change son implémentation interne, ce code casse silencieusement. Il manque une méthode publique bbox() sur la classe.

  c) readonly_session() non résolu (cli.py:230)

  session = store_obj.readonly_session()

  IceChainStore n'a pas de méthode readonly_session(). C'est soit du code mort, soit une méthode qui existe sur _repo directement. Si c'est self._repo.readonly_session(branch=self.branch), il faudrait un
   wrapper dans IceChainStore.

  d) L'exceedance confidence est calculée uniquement sur la fenêtre 24h (cli.py:276)

  conf_da = compute_ensemble_confidence(acc_ds, window_h=24, member_dim="member")

  Hardcodé à 24h alors que les fenêtres vont de 3h à 168h. La confiance pour une fenêtre 168h peut être très différente de celle à 24h.

  e) Le Dask Client est instancié mais jamais fermé (cli.py:400-404)

  Client(n_workers=workers, threads_per_worker=..., silence_logs=True)

  Le Client est créé dans le scope de la commande exceedance() mais jamais assigné à une variable ni fermé. Il devient le client global par défaut, ce qui fonctionne, mais c'est un anti-pattern qui peut
  laisser des processus orphelins.

  f) admin.iterrows() dans risk_engine.py:70 et aggregator.py:50

  iterrows() est O(n) avec une copie par ligne. Pour 26 admin-1 units c'est insignifiant, mais pour les 300 mentionnés dans la config, c'est potentiellement lent combiné avec
  regionmask.Regions([geom]).mask() qui est O(lat×lon) par appel. La mask devrait être pré-calculée une fois pour toutes les unités admin-1.

  g) member_dim="member" hardcodé dans _run_exceedance() (cli.py:265-266)

  Le Parquet GIK produit une dimension number (convention ECMWF) mais le parquet_to_virtual_dataset avec xr.concat(..., dim=member_idx) crée une dimension member. Si un seul fichier Parquet est chargé
  (pas de concat), la dimension s'appelle number. Le code assume member mais ça dépend du nombre de fichiers.
