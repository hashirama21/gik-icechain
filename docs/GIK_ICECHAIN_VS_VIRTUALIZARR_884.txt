GIK-IceChain - Response to VirtualiZarr #884 / icpac-igad Discussion #1
==========================================================================
Date: 2026-06-05
Authors: hashirama21, (SYNTHI-AI / E4DRR)


CONTEXT
-------
VirtualiZarr #884 and the ICPAC discussion raise three core problems when
converting large GRIB2/NetCDF archives (CMORPH, ECMWF IFS ENS) to IceChunk:

  1. OOM crash when writing virtual references directly to IceChunk at scale
  2. append_dim="time" memory blow-up on living datasets
  3. No manifest splitting -> single growing manifest -> degrading append speed

This document explains which problems gik-icechain solves, how, and which
remain open.


===========================================================================
PROBLEM 1: OOM WHEN WRITING VIRTUAL REFS TO ICECHUNK AT SCALE
===========================================================================

BACKGROUND (from #884)
-----------------------
nishadhka tried three strategies to write 236,688 CMORPH NetCDF virtual
references directly into an IceChunk store:

  - Batch mode:  workers virtualize files, xr.concat, write per-branch
  - Collect mode: coordinator collects refs, single to_icechunk() commit
  - Direct mode:  each worker commits independently

All three failed with OOM (exit 137) at ~28,000/236,688 files because the
coordinator accumulated ~85 KB of Kerchunk JSON per file in memory:
  28,000 files x 85 KB = ~2.4 GB at failure point
  236,688 files x 85 KB = ~20 GB at full scale

The workaround: PyArrow streaming ParquetWriter flushes each batch to disk
immediately, keeping coordinator RAM constant at ~10 MB.

HOW GIK-ICECHAIN SOLVES IT
---------------------------
gik-icechain avoids the OOM entirely through a different architecture:

  [1] PRE-BUILT PARQUET CATALOG (HuggingFace: E4DRR/gik-ecmwf-par)
      The Kerchunk references for ECMWF IFS ENS are already materialized
      as a flat-parquet catalog on HuggingFace. Each row encodes one
      (date, run_hour, member, step, variable) chunk ref as a byte array.
      This catalog was built incrementally as forecasts arrived - it is
      never rebuilt from scratch.

  [2] PER-DAY STREAMING VIRTUALIZATION (src/gik_icechain/conversion/)
      C1 processes one forecast day at a time:
        - Load 51 parquet files (one per ensemble member) via ThreadPoolExecutor
        - Parse with GIKFlatParquetParser -> ManifestStore (VirtualiZarr)
        - xr.concat along member dimension -> single virtual Dataset
        - commit_day() -> one IceChunk commit
      Memory per day: ~51 parquet files x ~a few KB refs = negligible.
      The coordinator never holds more than 1 day of refs in memory.

  [3] FREQUENT PARTIAL COMMITS
      One commit per forecast day, tagged with ISO-8601 timestamp:
        "2025-02-22T00Z" -> IceChunk snapshot SS9FE3YY38SV
      This is exactly what TomNicholas recommended in #884:
        "batching the files, and making partial, frequent commits"

STATUS: SOLVED
The OOM problem does not occur in gik-icechain because:
  - We never accumulate 236K file refs in memory at once
  - One day = 51 members x 85 steps x 5 variables = ~21,675 chunk refs
  - Committed immediately, freed from memory before next day starts


===========================================================================
PROBLEM 2: append_dim="time" MEMORY BLOW-UP ON LIVING DATASETS
===========================================================================

BACKGROUND (from #884)
-----------------------
VirtualiZarr's append_dim="time" approach failed at ~87,000 timesteps
because each new append reads back O(n) metadata (all existing time coords)
before writing, causing memory to scale with dataset size.

HOW GIK-ICECHAIN SOLVES IT
---------------------------
gik-icechain does not use append_dim="time" from VirtualiZarr.
Instead it uses IceChunk's native transaction model:

  session = repo.writable_session(branch="main")
  zarr_group = zarr.open_group(session.store, mode="a")
  # Write new day's data into a NEW date-keyed Zarr group
  day_group = zarr_group.require_group(date_str)
  session.commit(f"GIK ingest: {date_str}T{run_hour:02d}Z")

Each forecast day occupies its own Zarr group (keyed by ISO date string,
e.g. "2025-02-22"). There is no single time-dimension array that grows.
This sidesteps the O(n) metadata read entirely: appending day N+1 only
touches group "2025-02-23", not the existing 2025-02-22 group.

RESULT:
  - Memory for commit_day() is constant regardless of total days in store
  - 1200 days of IFS ENS = same RAM as 1 day during append
  - IceChunk's transaction log records snapshot history for rollback/replay

STATUS: SOLVED
The append_dim blow-up does not affect gik-icechain because the temporal
dimension is encoded as group keys (date strings), not as a zarr array
dimension. Each day is an independent write with no O(n) metadata scan.


===========================================================================
PROBLEM 3: MANIFEST SPLITTING
===========================================================================

BACKGROUND (from #884)
-----------------------
TomNicholas recommended manifest splitting along the time dimension to
prevent the IceChunk manifest from becoming a single growing file that
slows append and metadata scan as the archive grows.

IceChunk 2.x exposes ManifestSplittingConfig for exactly this purpose.

STATUS: IMPLEMENTED (commit fa42f60, 2026-06-05)

HOW GIK-ICECHAIN SOLVES IT
---------------------------
icechunk_writer._build_repo_config() now configures manifest splitting along
the `step` dimension (the forecast-horizon axis, which is the time-like axis
of each per-day array). Implemented with the *actual* IceChunk 2.0.5 API -
the API in the original recommendation (split_after_n_chunks) does not exist.

  REAL API (verified against icechunk 2.0.5):
    config.manifest = icechunk.ManifestConfig(
        splitting=icechunk.ManifestSplittingConfig(
            split_sizes=[
                (
                    icechunk.ManifestSplitCondition.AnyArray(),
                    [
                        (
                            icechunk.ManifestSplitDimCondition.DimensionName("step"),
                            1000,
                        )
                    ],
                )
            ]
        )
    )

  NOTE: The proposed `ManifestSplitCondition.split_after_n_chunks(1000)` does
  NOT exist in IceChunk 2.0.5. The real API is a per-(array, dimension) size
  map: split_sizes = [(array_condition, [(dim_condition, max_positions)])].

CONFIGURATION (configs/default.yaml -> component1.icechunk):
    manifest_splitting: true       # enable/disable
    manifest_split_dim: "step"     # dimension to split along
    manifest_split_size: 1000      # max index positions per manifest fragment

DESIGN NOTE - why split on `step`, not `time`:
gik-icechain does not have a single global time axis (see PROBLEM 2): each
forecast day is its own date-keyed Zarr group with arrays shaped
(member=51, step=85, lat=721, lon=1440). Within an array, only `member` and
`step` have multiple chunks (lat/lon are single full-grid chunks). `step` is
the natural time-like axis, so manifests are split along it. This bounds each
manifest fragment regardless of how many day-groups the store accumulates.

IMPACT: Low for current scale (< 50 committed days), high at 1200+ days -
now mitigated. Validated: repo config builds correctly with the splitting
config attached; 38 byte-range/manifest/virtualizer unit tests pass.

ADDITIONAL OPEN ISSUES DISCOVERED DURING DEVELOPMENT

ISSUE A: ECMWF S3 PUBLIC DATA RETENTION (~15 MONTHS)
------------------------------------------------------
The GIK HuggingFace catalog covers 2024-03-01 to 2026-02-18 (720 days).
The public ECMWF S3 bucket (s3://ecmwf-forecasts) retains forecast data
for approximately 15 months. Dates older than ~15 months return 403
Forbidden when byte-range reads are attempted in C2 (exceedance).

Consequence:
  - C1 (ingest virtual refs): works for all catalog dates (metadata only)
  - C2 (fetch GRIB2 bytes for exceedance): works only for last ~15 months
  - Historical flood validation on 2024-04-26 (Kenya MAM floods): Forbidden

Solution for full historical archive: ECMWF subscription (MARS archive
access) or local GRIB2 mirror for dates older than 15 months.

UPDATE 2026-06-09: the ~15-month figure is conservative. An E2E run on
2024-04-24 (Kenya/Tanzania MAM 2024 floods, ~26 months old) fetched all
51 members / 1530 chunks (1318 MB) from s3://ecmwf-forecasts with
n_failed_files=0. So historical reads currently work well beyond 15 months;
the retention horizon is not a hard 15-month cliff in practice. Treat older
dates as best-effort (the per-file fetch tolerates missing objects, see
ISSUE-5) rather than guaranteed-Forbidden.

ISSUE B: AWS_ENDPOINT_URL COLLISION (FIXED: commits d051604, b2b00ab, fa42f60)
------------------------------------------------------------------------------
Running the pipeline sets AWS_ENDPOINT_URL=http://MinIO-IP:9000 for
IceChunk to write to local MinIO. The manifest-aware C2 path inherited this
env var, redirecting all ECMWF S3 byte-range reads to MinIO (403 Forbidden).

Fix evolution (three iterations until robust):
  1. d051604: fsspec with explicit endpoint_url - broke on path-style vs
     virtual-hosted bucket addressing.
  2. b2b00ab: switched from fsspec/boto3 (anon=True blocked by ECMWF) to
     obstore S3Store with skip_signature=True (same mechanism as IceChunk).
  3. fa42f60: pass explicit endpoint to obstore S3Store so the env var is
     never consulted:
       S3Store(bucket, region=s3_region, skip_signature=True,
               endpoint=f"https://s3.{s3_region}.amazonaws.com")

Verified: fetch succeeds against the real AWS endpoint even with
AWS_ENDPOINT_URL=MinIO still set in the environment.
The same explicit-endpoint pattern is used by IceChunk's Rust S3 client in
icechunk_writer._build_repo_config().

ISSUE C: ICECHUNK 2.x API MIGRATION (FIXED: commits f19d56f, d051604)
----------------------------------------------------------------------
IceChunk 2.0.5 changed all_virtual_chunk_locations() from returning a
{chunk_key: location} dict to returning a flat list of unique URIs.
This broke the manifest-aware C2 loader which needed (url, offset, length)
per chunk.

Fix: ported _extract_virtual_chunk_refs() to use
store.array_chunk_iterator(array_path) which yields batches of:
  (coords, types, uris, offsets, lengths, extra)
providing (url, offset, length) per virtual chunk without any S3 fetch.
Validated: 1530 refs extracted correctly for 2024-04-26.

ISSUE D: CLUSTER DISPATCH IN C3 (FIXED: commit d8e2c19)
--------------------------------------------------------
CRMAModel was instantiated with a single climate cluster (EQUATORIAL_EAST)
applied to all 155 admin-1 units. Units in Somalia (horn_arid), Ethiopia
(great_rift), South Sudan (nile_basin) received CPT weights calibrated for
equatorial Kenya/Tanzania - scientifically incorrect for ~80% of units.

Fix: _build_pcode_cluster_map() maps each admin-1 pcode to its correct
EastAfricaCluster via ISO3 country code (from shapeGroup column).
One CRMAModel per cluster is built and dispatched per unit in _process_day().

ISSUE E: NON-UNIFORM STEP HOURS IN MANIFEST-AWARE LOADER (FIXED: commit 6a5bfae)
-------------------------------------------------------------------------------
GIK IFS ENS forecast steps are NON-UNIFORM: 3-hourly out to 144 h (step
indices 0-48), then 6-hourly to 360 h (indices 48-84) - 85 steps total.

The manifest-aware loader built a UNIFORM step coordinate
(np.arange(max_steps) * step_resolution_h, with step_resolution_h=6). This
caused two defects:
  1. The 3 h accumulation window was unusable (6 h spacing) and was being
     skipped entirely, dropping it from the exceedance store (window dim
     7 -> 6, which then collided with the existing 7-window store on append).
  2. CORRECTNESS BUG: every step in the 3-hourly region was mislabelled -
     index 8 became "48 h" instead of the true "24 h", so all exceedance
     values in the first 144 h were assigned to the wrong forecast hours.

Fix (two parts):
  a. manifest_store._read_step_hours() reads the ACTUAL step coordinate from
     the IceChunk store; _assemble_dataset() uses the real (non-uniform)
     hours instead of arange * resolution.
  b. accumulation_for_window() now looks up the lagged value by actual
     forecast hour (tp[h] - tp[h-w]) via reindex, not by a fixed index
     offset. This is correct for non-uniform spacing:
       - h - w <= 0           -> raw (whole history so far)
       - h - w is a stored step -> tp[h] - tp[h-w]
       - h - w positive but absent (3 h window in the 6-hourly region) -> NaN

Result: ALL 7 accumulation windows (3, 6, 12, 24, 48, 72, 168 h) are
preserved AND correct. The 3 h window is valid out to 144 h (where 3-hourly
data exists) and NaN beyond. A config flag
(component2.skip_subresolution_windows) controls whether a window finer than
the detected step spacing is skipped with a warning or raises. 175 unit
tests pass.


ISSUE F: C2 EXCEEDANCE ALWAYS ZERO - tp UNIT MISMATCH (FIXED 2026-06-09)
------------------------------------------------------------------------
Every exceedance run produced exceedance_prob = 0.0 across the ENTIRE grid
(all 7 windows x 6 return periods), regardless of forecast date - so C3 risk
fell back to the BN prior for all admin-1 units (196 identical scores) and
never produced a non-Green signal. This was the root cause of "no Orange/Red"
(ISSUE-1 in docs/ISSUES.md).

ROOT CAUSE: ECMWF IFS `tp` is decoded in METRES (verified: raw last-step
member-0 East Africa max 0.349, mean 0.044 -> metres). The CMORPH GEV
return-period thresholds are in MILLIMETRES (rp_2y ~0.8-187 mm). The
comparison `(tp_worst > threshold)` in exceedance.py compared metres
(~0.05-0.35) against mm thresholds (~1-450) -> never True -> 0 everywhere.
Even the minimum rp_2y = 0.835 mm was never exceeded by any of 51 members,
which is impossible for a real rainfall field unless the units are off by
~1000x. The accumulation/confidence code already ASSUMED mm ("max(median,
1 mm)"), confirming mm was the intended unit.

FIX: convert tp m -> mm once at C2 entry, before accumulation, so the whole
chain (accumulations, ensemble confidence, exceedance) is unit-consistent.
  - config: component2.precip_scale_to_mm (default 1000.0; set 1.0 if the
    source is already mm). GRIB attrs carry no usable `units`, so this is a
    config constant, not auto-detected.
  - cli.py::_process_exceedance_day multiplies day_ds["tp"] by the scale
    before compute_rolling_accumulations (covers both the manifest-aware and
    the xr.open_zarr paths); passed via worker_args from _run_exceedance.

VALIDATED: re-run on 2025-11-20 -> exceedance_prob max 1.0, 26,280 non-zero
cells; per-unit probabilities now differentiate spatially (previously every
unit was identical). 2024-04-24 -> max 1.0, 12,256 non-zero cells.


ISSUE G: C3 HAZARD DILUTED BY MEAN AGGREGATION (FIXED 2026-06-09)
-----------------------------------------------------------------
After ISSUE F, exceedance was non-zero on the grid but admin-1 risk labels
were still all Green. Cause: run_risk_batch aggregated the gridded exceedance
hazard to each admin-1 polygon with the MEAN (aggregate_to_admin1 default
stat="mean"), so a localized flood peak (a few cells at prob 1.0) was averaged
away over the whole unit. The config block component3.aggregation existed
(method, min_coverage_fraction) but was never wired into run_risk_batch.

FIX (best practice for a flood EWS: "is ANY part of the unit at risk"):
  - aggregator.aggregate_to_admin1 now also accepts a percentile stat "pNN"
    (e.g. "p90", "p95") in addition to "mean"/"max"/"area_weighted".
  - run_risk_batch / _process_day take hazard_stat + min_coverage and apply
    them to the exceedance aggregations (24h/72h/7d). Observed GPM rainfall
    stays "mean" (an areal quantity).
  - component3.aggregation.method default changed "mean" -> "max" and is now
    wired from config via cli._run_risk. This is complementary to the
    Spatial_Coverage BN node, which already encodes the % of the unit's area
    above threshold.

VALIDATED: 2024-04-24 with max aggregation -> per-unit exceedance_24h_5y now
reaches 1.0 (e.g. MDG_Amoron'i Mania, MDG_Melaky) and risk probabilities lift
to p_yellow 0.31 / p_orange 0.125 / p_red 0.057 (vs 0.091/0.029/0.010 before).

DESIGN NOTE - why labels can still read Green on a severe day: the CRMA
Compound_Risk CPT is intentionally compound-conservative. A single-day
FORECAST spike alone (Forecast_Hazard=High, but Spatial_Coverage=Local,
API=Dry, no observed rain, no multi-day persistence) scores into the "mid"
bucket -> Green remains the MAP (argmax) class while p_yellow/p_orange rise.
Escalation to Yellow/Orange/Red requires corroborating evidence: spatial
coverage >= regional (>=25% of the unit), antecedent wetness (API), observed
rainfall (GPM IMERG - currently absent, see ISSUES.md ISSUE-11), or multi-day
persistence (API + consecutive-signal build-up over a date RANGE, not a single
day). The argmax/MAP label is retained (standard for a discrete BN); the full
probability vector is preserved per unit for probability-based dashboards.

ISSUE I: ICECHUNK TAG IMMUTABILITY - RE-INGEST RETURNS STALE SNAPSHOT (FIXED 2026-06-12)
----------------------------------------------------------------------------------------
Re-running C1 for a date that was already ingested created a fresh IceChunk
commit (branch HEAD advanced, new data written) but the time-travel and listing
APIs kept returning the OLD snapshot.

OBSERVED: 01_component1_walkthrough.ipynb snapshot list on 2026-06-12 showed
2025-11-19 pointing at the 2026-06-09 commit (CYEVPYV0GHZ4) even though that day
had just been re-ingested (BE40GYNHWZM6). A genuinely new date (2025-11-18)
correctly showed the same-day commit. Time-travel checkout_as_of(2025-11-19)
would therefore have served stale data.

ROOT CAUSE: the per-day tag scheme ("{date}T{run_hour:02d}Z"). IceChunk tags are
IMMUTABLE and - verified on 2.0.5 - a tag NAME CANNOT BE REUSED even after
delete_tag:
    create_tag(...) -> "icechunk does not allow tag reuse and tag was already
                        deleted `2025-11-19T00Z`"
So a re-ingest cannot move its tag. commit_day swallowed the create_tag failure
at debug level, leaving the tag pinned to the first commit. checkout_as_of,
list_snapshots and open_latest all resolved snapshots via tags (list_tags /
lookup_tag) -> they served the stale first commit.

FIX: resolve "current snapshot for forecast_date X" from BRANCH ANCESTRY plus
commit metadata, never from tags. New _snapshots_by_date() walks
repo.ancestry(branch=...) (newest-first) and keeps the first SnapshotInfo per
metadata["forecast_date"] -> the most recent re-ingest wins.
  - conversion/icechunk_writer.py (IceChainStore): checkout_as_of /
    list_snapshots / open_latest rewritten on _snapshots_by_date; the obsolete
    tag helper (_tag_before_or_on) was removed. commit_day still creates a tag
    best-effort (human label, non-authoritative; failure logged at debug).
  - exceedance/icechunk_output.py (DecisionStore): same fix to checkout_as_of /
    list_dates (dormant store - outputs.exceedance_icechunk_uri empty - fixed for
    consistency).

VALIDATED: regression tests test_commit_day_reingest_resolves_fresh (C1) and
test_reingest_resolves_fresh (DecisionStore) assert the immutable tag stays on
the first commit while the public API surfaces the re-ingested data; 6 IceChunk
store tests pass. No tag-based resolution (list_tags / lookup_tag) remains in
src/.

GENERAL LESSON: for any IceChunk store keyed by a logical date, resolve the
current snapshot via branch ancestry + commit metadata, not by tag name. Tags
are write-once labels, not movable pointers.

===========================================================================
RECOMMENDED NEXT STEP FOR THE ICPAC DISCUSSION
===========================================================================

The "small starting step" proposed by nishadhka (1 variable + 1 month +
1 member, batched commits + manifest splitting) is validated by gik-icechain
at larger scale. The key insight to share with the icpac-igad discussion:

  The OOM is not intrinsic to IceChunk virtual stores - it only occurs when
  all references are written in a single transaction. Writing N chunks in
  B-chunk batches with frequent commits and date-keyed group structure keeps
  memory constant at O(B), not O(N).

  For 236K CMORPH files: split by day (one commit per ~480 30-min files),
  not by batch of arbitrary size. IceChunk's snapshot history then gives
  you a time-indexed transaction log for free.

  Manifest splitting (now implemented in gik-icechain, commit fa42f60):
  use the real IceChunk 2.0.5 API - ManifestSplittingConfig(split_sizes=[
  (ManifestSplitCondition.AnyArray(), [(ManifestSplitDimCondition.
  DimensionName("<time-axis>"), N)])]). The split_after_n_chunks helper
  referenced in earlier discussion does not exist in 2.0.5; the real config
  is a per-(array, dimension) max-positions map. For CMORPH's single global
  time-axis store, split on "time" every ~8760 positions (1 year of hourly)
  or per-month for finer fragments.

  No remaining open items on the manifest/append/OOM axis. The only hard
  constraint is ECMWF S3 public data retention (~15 months) for C2 byte-range
  reads, which requires a MARS subscription for older historical dates.
